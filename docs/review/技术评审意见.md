# 技术架构评审意见 — 内部产品打包分发系统

> **评审人**: 技术架构师  
> **评审日期**: 2025-07-24  
> **评审对象**: PRD v1.0 + 现有代码 (DeployManager)  
> **结论**: **有条件通过**，需在 5 个关键技术点上完成确认后方可进入开发。

## 一、整体架构评价

### 1.1 现有架构

```
┌──────────────────────────────────────────────────────────┐
│  浏览器 (Vue 3 SPA)                                       │
├──────────────────────────────────────────────────────────┤
│  SpringBoot 2.7.18 (Tomcat)                              │
│  ├── Controller: Project / File / Infra / Package        │
│  ├── Service: PackageService (异步打包核心)                │
│  │   ├── FreeMarker → 生成 .ps1 启停脚本                  │
│  │   ├── Zip4j → AES-256 加密 ZIP                        │
│  │   └── MinIO Client → 下载组件 / 上传产物               │
│  └── MyBatis-Plus → MySQL 8.0                            │
├──────────────────────────────────────────────────────────┤
│  MinIO (对象存储)      MySQL 8.0 (元数据)                  │
└──────────────────────────────────────────────────────────┘
```

### 1.2 架构评价

| 维度 | 评价 | 说明 |
|------|------|------|
| **分层清晰度** | ★★★★☆ | Controller → Service → Mapper 三层标准，职责分明 |
| **可复用性** | ★★★★☆ | PRD 中 70% 功能直接改造现有代码，新增 License/User 模块独立 |
| **扩展性** | ★★★☆☆ | 基础服务类型硬编码在枚举和模板中，P1 需求"自定义服务类型"需要重构 |
| **性能** | ★★★☆☆ | 异步打包用 `@Async + Semaphore(2)` 方案简单可行，但 `ConcurrentHashMap` 存日志无持久化 |
| **安全性** | ★★☆☆☆ | 现有代码无认证、无授权、无 HTTPS 强制、密码明文传参到 FreeMarker 模板 |

### 1.3 架构决策建议

**保持 SpringBoot + Vue 3 + MinIO + FreeMarker 主架构**，无需更换技术栈。但需补充：

1. **安全层**: 新增 Spring Security + JWT 认证过滤器，作为 PRD 中"用户认证与权限"模块的基础
2. **License 模块**: 独立 `LicenseService`，与打包引擎通过接口解耦（`LicenseProvider` 接口），便于 mock 和后续替换
3. **模板引擎**: FreeMarker 模板从 `services/start-xxx.ps1.ftl` 迁移到 `services/start-xxx.bat.ftl`，保留 .ps1 模板做灰度切换

## 三、打包引擎评审

### 3.1 现有流程分析

现有 `PackageService.executePackageAsync()` 是一个硬编码的流水线：

```
验证配置 → 收集JAR → 收集JDK → 收集Vue+Nginx → [MySQL] → [MinIO] → [Engine]
→ 生成脚本 → 打包ZIP → 上传MinIO → 清理临时文件
```

### 3.2 新需求适配评估

| 新需求 | 现有支持 | 改造量 | 风险 |
|--------|---------|--------|------|
| License 注入打包 | ❌ 无 | 🟡 中 | 在"生成脚本"步骤后增加"注入 License"步骤，约 20 行代码 |
| 多组件版本组合 | ✅ 已有 | 🟢 低 | 现有 `*_component_id` 外键机制已支持 |
| Redis 组件支持 | ❌ 无 | 🟡 中 | 新增 `collectInfraComponentById(redis, "redis")` + 启停脚本模板 |
| 打包进度 12 步（原 9 步） | 🔧 需改 | 🟢 低 | 调整 progress 百分比分配 |

### 3.3 关键改进建议

**问题 1: 硬编码流水线 vs 可配置流水线**

现有 `executePackageAsync()` 是一个 200+ 行的巨型方法，每个组件类型硬编码。随着 Redis 等新组件加入，该方法会越来越膨胀。

**建议**: 引入**责任链模式**或**步骤注册器**重构：

```java
// 定义打包步骤接口
interface PackageStep {
    String getName();           // 步骤名称
    int getProgressWeight();    // 进度权重
    boolean isRequired(Project project);  // 是否需要执行
    void execute(Project project, Path packageDir) throws Exception;
}

// PackageService 中
List<PackageStep> steps = List.of(
    new CollectJarStep(),
    new CollectJdkStep(),
    new CollectVueNginxStep(),
    new CollectMysqlStep(),    // 按需
    new CollectRedisStep(),    // 新增
    new CollectMinioStep(),    // 按需
    new CollectEngineStep(),   // 按需
    new GenerateScriptsStep(),
    new InjectLicenseStep(),   // 新增
    new GenerateReadmeStep(),  // 新增
    new CreateEncryptedZipStep(),
    new UploadToMinioStep()
);
```

这样新增组件只需新增 Step 类，不修改 PackageService 核心逻辑。

**问题 2: License 注入时机**

PRD 中 License 在打包时生成（销售输入客户名+天数），但 License 生成可能失败（加密库不可用等），此时打包已进行到 70%+。建议：

- **前置生成**: 在打包任务启动前先生成 License 并入库，打包时仅做文件复制
- **打包 API 改造**: `POST /api/package/start` 增加 `licenseId` 参数，先校验 License 存在且有效

**问题 3: 并发控制**

现有 `Semaphore(2)` + `activeProjectTasks` 方案正确，但 `taskLogs` 用内存 `ConcurrentHashMap` 存储：
- 重启后日志丢失
- 多实例部署时无法共享

建议：日志持久化到 `operation_log` 表或独立的 `package_task_log` 表。

## 四、License 体系设计

### 4.1 License 生成（技术方案）

PRD 提到"License 生成代码待提供"，这里给出标准技术方案：

**推荐方案: 非对称加密 + 数字签名**

```
生成流程:
  1. 系统持有 RSA 私钥（服务端安全存储，不对外暴露）
  2. 输入: 客户名 + 项目ID + 过期时间 + 机器码(可选)
  3. 构造 License 载荷 JSON → SHA256 摘要 → RSA 私钥签名
  4. 将 JSON + 签名打包为 license.dat（Base64 + 分隔符）
  
校验流程（JAR 端）:
  1. 读取 license/license.dat
  2. 解析载荷和签名
  3. 用内置公钥验证签名 → 确认未被篡改
  4. 检查过期时间 → 决定是否允许启动
```

**关键设计点**:
- **公私钥分离**: 私钥仅存打包系统（不进入产物），公钥硬编码在 JAR 中
- **防篡改**: 签名验证保证 License 文件不可伪造
- **过期检查**: JAR 启动时读取 `expire_date`，与系统时间比对
- **防时间回拨**: 记录最后启动时间戳，防止用户回拨系统时间绕过过期

### 4.2 License 注入打包

现有打包流水线在"生成脚本"后（progress 70%）是注入的最佳时机：

```java
// 在 generateScripts 和 createEncryptedZip 之间插入
updateTaskProgress(taskId, 75, "注入License文件...");
Path licenseDir = packageDir.resolve("license");
Files.createDirectories(licenseDir);
// 从 MinIO 下载已生成的 license.dat
LicenseRecord license = licenseMapper.selectById(licenseId);
downloadFromMinio(license.getMinioBucket(), license.getMinioObjectKey(),
    licenseDir.resolve("license.dat"));
```

### 4.3 License 续期流程

PRD 的续期设计合理："生成全新 License 文件 → 客户替换 → 重启"。需补充：

1. **续期时的旧 License 状态**: 续期后旧 License 自动标记为 `EXPIRED`，防止一个客户持有多个有效 License
2. **续期次数限制**: 建议 `renew_count` 字段记录，可配置上限（如最多续期 5 次）
3. **续期通知**: 在 JAR 启动日志中打印"License 将于 X 天后过期"，提示客户提前续期

### 4.4 License 安全存储

| 存储位置 | 内容 | 安全措施 |
|---------|------|---------|
| MySQL `license_record` | 元数据（客户名、过期时间、状态） | 数据库访问控制 |
| MinIO `licenses/` bucket | license.dat 文件 | Bucket 访问策略限制 |
| JAR 内置 | RSA 公钥 | 代码混淆保护 |
| 打包系统配置 | RSA 私钥 | 环境变量/密钥管理服务，不提交代码仓库 |

## 五、启动脚本：PowerShell → Batch 迁移

### 5.1 技术差异分析

| 特性 | PowerShell (.ps1) | Batch (.bat) |
|------|-------------------|--------------|
| Windows 兼容性 | Win7+ 需安装/升级 PS | Win XP+ 原生支持 |
| 进程管理 | `Start-Process -PassThru` 获取 PID | `start /b` + `wmic` 或 `tasklist` 解析 |
| 后台启动 | 原生 `-WindowStyle Hidden` | `start /b` + 窗口隐藏较复杂 |
| 错误处理 | `$ErrorActionPreference` + try/catch | `%ERRORLEVEL%` + `goto` |
| 字符串处理 | 强大 | 极为有限 |
| JSON/配置解析 | 原生 | 不支持，需第三方工具 |
| 编码 | UTF-8 (需 BOM) | GBK 默认（中文乱码风险） |

### 5.2 Batch 脚本关键技术点

**1. 进程管理与 PID 文件**

Batch 获取 PID 的方法：
```batch
:: 方式一: wmic (Windows 7+)
for /f "tokens=2" %%a in ('wmic process where "name='mysqld.exe'" get processid ^| find /i "0-9"') do set PID=%%a

:: 方式二: PowerShell 内嵌（推荐）
powershell -Command "(Start-Process -FilePath 'bin\mysqld.exe' -ArgumentList '--defaults-file=my.ini' -WindowStyle Hidden -PassThru).Id" > pid\mysql.pid
```

**建议**: 对于复杂的进程管理（后台启动、PID 获取），在 .bat 中调用内嵌 PowerShell 命令，而非纯 Batch 实现。这样既兼容所有 Windows 版本，又不失功能完整性。

**2. 中文编码**

Batch 文件默认 GBK 编码，如果包含中文输出（如"MySQL 启动失败"），需：
- 模板生成时用 `charset GBK` 写入
- 或在 .bat 开头添加 `chcp 65001 > nul` 切换到 UTF-8

**建议**: 统一使用 `chcp 65001` 方案，与 FreeMarker 模板 UTF-8 编码一致。

**3. 服务启动顺序与健康检查**

Batch 实现启动后等待服务的推荐模式：
```batch
:: 启动 MySQL 并等待就绪
call services\start-mysql.bat
:wait_mysql
timeout /t 2 /nobreak > nul
powershell -Command "& 'mysql\bin\mysql.exe' -u root --port=%MYSQL_PORT% -e 'SELECT 1' 2>$null; exit $LASTEXITCODE"
if %ERRORLEVEL% neq 0 goto wait_mysql
```

**4. 停止脚本**

Batch 实现 PID 文件停止：
```batch
set /p PID=<pid\mysql.pid
taskkill /PID %PID% /F 2>nul
del pid\mysql.pid 2>nul
```

### 5.3 迁移工作量评估

| 模板文件 | 原格式 | 新格式 | 复杂度 |
|---------|--------|--------|--------|
| `start.ps1.ftl` | PowerShell | `start.bat.ftl` | 🟡 中 |
| `stop.ps1.ftl` | PowerShell | `stop.bat.ftl` | 🟢 低 |
| `start-jar.ps1.ftl` | PowerShell | `start-jar.bat.ftl` | 🟢 低 |
| `start-mysql.ps1.ftl` | PowerShell | `start-mysql.bat.ftl` | 🔴 高（含初始化逻辑） |
| `start-redis.ps1.ftl` | 无 | `start-redis.bat.ftl` | 🆕 新增 |
| 其他 6 个模板 | PowerShell | Batch | 🟡 中 |

**总估**: 约 12 个模板文件需要重写/新增，其中 MySQL 模板最复杂（含数据目录初始化、账密注入、健康检查）。

## 六、关键风险清单

### 🔴 高风险

| 编号 | 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|------|---------|
| **R1** | **Windows 便携版基础服务兼容性** | MySQL/Redis/MinIO/Nginx 的 Windows 绿色版可能在某些 Win10/11 版本上无法正常运行 | 中 | 1. 建立 Windows 兼容性测试矩阵（Win10 21H2/22H2, Win11 21H2/22H2/23H2）<br>2. 各服务锁定具体便携版版本号<br>3. 准备 Docker Desktop 备选方案 |
| **R2** | **License 加密方案未确定** | License 模块是整个系统的核心价值所在，如果加密方案不可靠，系统形同虚设 | 高 | 1. 立即要求开发团队提供 License 生成代码的接口规范（输入/输出格式）<br>2. 先实现基于 RSA 签名的标准方案作为基线<br>3. 预留 LicenseProvider 接口便于替换 |
| **R3** | **打包体积过大（GB 级）** | JDK(~200MB) + MySQL(~500MB) + Redis + MinIO + Nginx + Engine + JAR，单包可达 2-5GB，内网下载也可能超时 | 中 | 1. MinIO 下载支持断点续传（前端）<br>2. 考虑组件预缓存（JDK 等公共组件不重复下载）<br>3. 设置下载超时时间（如 30 分钟） |

### 🟡 中风险

| 编号 | 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|------|---------|
| **R4** | **MySQL 密码在 FreeMarker 模板中传递** | `dbPassword` 作为模板变量传入，如果模板渲染出错可能泄露到日志 | 低 | 1. 模板渲染时对密码做脱敏处理<br>2. 日志中过滤密码字段<br>3. 打包完成后立即清理临时目录 |
| **R5** | **Redis 组件在 Windows 上无官方支持** | Redis 官方不提供 Windows 版，第三方移植版（如 MSOpenTech/redis）可能版本落后 | 高 | 1. 调研 Windows Redis 替代方案（Memurai 或 WSL2）<br>2. 或将 Redis 改为可选组件，标注"实验性支持" |
| **R6** | **打包中间状态恢复** | 如果打包在第 7 步失败（如 MinIO 下载超时），已下载的 6 个组件临时文件能否复用？ | 低 | 1. 每次打包使用独立 taskId 临时目录<br>2. 失败后全部清理（当前逻辑）<br>3. 后续可考虑组件级缓存目录 |
| **R7** | **project 表字段膨胀** | project 表已有 45+ 个字段，PRD 新增后接近 60 个字段，违反数据库范式 | 低 | 1. 拆分为 `project`（基本信息）+ `project_config`（配置详情）<br>2. MVP 阶段可接受，但需在 P1 重构 |

### 🟢 低风险

| 编号 | 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|------|---------|
| **R8** | **销售输入的密码明文传输** | ZIP 密码从前端传到后端，如果未启用 HTTPS 可能被拦截 | 低 | 内网部署降低风险，但仍建议前端做 base64 编码 + HTTPS |
| **R9** | **打包任务无超时机制** | 如果某个组件下载卡住，打包任务会永远 RUNNING | 低 | 增加打包任务总超时（如 30 分钟），超时自动标记 FAILED |
| **R10** | **并发 2 个任务共享磁盘 IO** | 两个打包任务同时下载大文件，可能互相影响速度 | 低 | 当前限制 2 并发可接受，后续可考虑 IO 限速 |

## 七、技术选型确认项

以下事项需要产品/开发团队在进入开发前明确确认：

| 编号 | 确认项 | 当前状态 | 建议 |
|------|--------|---------|------|
| **C1** | License 加密算法 | ❌ 待提供 | 建议 RSA-2048 + SHA256，公钥内置于 JAR |

## 八、总结与建议

### 8.1 总体评价

PRD 对业务需求的描述清晰完整，与现有代码的差距分析准确（约 70% 复用率）。技术方案整体可行，**SpringBoot + Vue 3 + MinIO + FreeMarker** 架构无需调整。

### 8.2 核心改进建议（按优先级）

1. **P0 - License 方案先行**: 在开发其他模块前，先确定 License 加密方案和 JAR 端校验接口。这是整个系统的价值核心。

2. **P0 - 安全层优先实现**: 在改造现有接口前，先完成认证授权（Spring Security + JWT），否则所有改造接口都需要返工。

3. **P0 - Windows 兼容性验证**: 立即启动 MySQL/Redis/MinIO/Nginx 在目标 Windows 版本上的绿色版测试。

4. **P1 - 打包引擎重构**: 将硬编码流水线改为可注册的步骤链，为后续新增组件（Redis、自定义服务）铺路。

5. **P1 - 数据库字段清理**: 合并 PRD 中与现有代码重复的字段（mysql_username/db_username 等），避免迁移时的数据冲突。

6. **P2 - project 表拆分**: 将配置详情拆分到独立表，防止单表字段膨胀。

### 8.3 推荐开发顺序

```
Phase 1 (基础安全):      用户认证 + 角色权限 + JWT
Phase 2 (License 核心):   License 生成/续期 + LicenseProvider 接口
Phase 3 (打包增强):       Redis 支持 + License 注入 + .bat 模板迁移
Phase 4 (UI 改造):        Vue 3 前端 + License 管理页 + 用户管理页
Phase 5 (测试验证):       Windows 兼容性测试 + 端到端集成测试
Phase 6 (上线准备):       文档 + 部署脚本 + 监控告警
```
